# Conformance corpus

Real and generated `.phyphox` files that, together with the shipped experiment
collection, exercise **every element and attribute the format specification
models** (`spec/*.yml`). This is the seed of the phase 4 conformance corpus:
files the app and editor test suites can parse to catch regressions in the
format surface that the shipped experiments alone never touch.

- `valid/` — files collected from real use: test files built during feature
  development, collaboration and support-request experiments, and student
  project files, curated down to a set where each file contributes constructs
  the shipped collection does not cover. Two folders are renamed from their
  originals at the maintainer's request; one systematic set (`rate-test/`)
  sweeps every `rateStrategy` value across several rates on purpose. Network
  addresses in these files are examples or non-routable; credentials have been
  replaced with placeholders.
- `generated/` — hand-written fixtures for the spec surface that no collected
  file exercises either: the inverse and hyperbolic trigonometry modules,
  `gcd`/`lcm`, `butterworth`, the `events` block of saved states, `appleBan`,
  and a set of rarely used view, network and I/O attributes. Each file states
  its purpose in a comment.
- `manifest.yml` — generated by `tools/corpus_manifest.py`; per file, the
  declared format version and the constructs it adds over the shipped
  collection. Regenerate it after changing the corpus.

Every file here is expected to validate cleanly:

    .venv/bin/python tools/validate_experiments.py corpus

The docs build enforces this (`tools/hooks.py`), so a spec change that
invalidates a corpus file — or a corpus file that drifts from the spec —
fails `mkdocs build --strict`.

These files are configurations for parsing, not maintained experiments: a
`bluetooth` fixture will not find its device and a `network` fixture will not
reach its example server. That is fine — their job is to hold the parser
surface still.
